# Deployment

Ember is **one Python service** plus **hosted PostgreSQL**. There is no second
frontend deployment, no CORS configuration, and no cross-domain cookie problem.

```
        ┌────────────────────────┐         ┌──────────────────────┐
users ─►│  Ember (FastAPI)       │────────►│  PostgreSQL (Neon)   │
        │  Render / Fly / Railway│  TLS    │  pooled connection   │
        │  serves UI + API       │         │  PITR backups        │
        └────────────────────────┘         └──────────────────────┘
```

Production must not depend on localhost services, the local filesystem, SQLite,
in-memory application state, or a developer's machine. Ember depends on exactly
one external resource: the PostgreSQL URL.

## 1. Database (Neon)

1. Create a project at <https://neon.tech> and a database named `ember`.
2. Copy the **pooled** connection string (the host contains `-pooler`).
3. Convert it for SQLAlchemy:

```
postgresql+psycopg://USER:PASSWORD@ep-xxx-pooler.REGION.aws.neon.tech/ember?sslmode=require
```

`postgres://` and `postgresql://` are also accepted — `Settings` normalises the
driver automatically. Anything that is not PostgreSQL is rejected at startup.

Neon's free tier suspends idle compute; `pool_pre_ping=True` handles the
reconnect, at the cost of one cold-start delay on the first request after idle.

## 2. Environment variables

| Variable | Required | Production value |
| --- | --- | --- |
| `DATABASE_URL` | ✅ | Neon pooled URL |
| `SESSION_SECRET` | ✅ | `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `ENVIRONMENT` | ✅ | `production` |
| `FRONTEND_URL` | ✅ | `https://your-domain` |
| `BACKEND_URL` | ✅ | `https://your-domain` (same) |
| `GITHUB_CLIENT_ID` | for GitHub | from the OAuth app |
| `GITHUB_CLIENT_SECRET` | for GitHub | from the OAuth app |
| `GITHUB_OAUTH_REDIRECT_URI` | for GitHub | `https://your-domain/api/auth/github/callback` |
| `GITHUB_OAUTH_SCOPES` | — | `read:user user:email` |
| `STORE_GITHUB_TOKENS` | — | `false` |
| `SESSION_COOKIE_NAME` | — | `ember_session` |
| `SESSION_MAX_AGE_DAYS` | — | `30` |
| `POLLING_INTERVAL_MS` | — | `4000` |
| `LOGIN_MAX_ATTEMPTS` | — | `8` |
| `LOGIN_ATTEMPT_WINDOW_MINUTES` | — | `15` |
| `ADMIN_EMAILS` | — | comma-separated; **server-side only** |
| `ADMIN_GITHUB_USERNAMES` | — | comma-separated; **server-side only** |
| `EMAIL_BACKEND` | — | `auto` (default), `smtp`, or `console` |
| `SMTP_HOST` / `SMTP_FROM` / `SMTP_*` | for email | Enables real delivery of reset and verification mail |
| `REQUIRE_EMAIL_VERIFICATION` | — | Gate new email/password accounts (requires SMTP) |

`ENVIRONMENT=production` turns on `Secure` cookies and disables `/api/docs` and
the OpenAPI schema.

`ADMIN_*` are read only by the server and never rendered into a page or returned
by an endpoint.

**Email:** password reset and verification need real delivery in production. Set
`SMTP_HOST` and `SMTP_FROM` (any transactional provider). Without SMTP the app
falls back to logging mail, which is fine for a private trial but means reset
links never reach users. If `REQUIRE_EMAIL_VERIFICATION=true`, SMTP is mandatory
— the app refuses to boot otherwise. See [EMAIL.md](EMAIL.md).

## 3. Deploy

### Render (blueprint included)

`render.yaml` is at the repository root:

- Docker build from `backend/Dockerfile`
- `preDeployCommand: alembic upgrade head`
- `healthCheckPath: /api/health`
- `SESSION_SECRET` generated by Render; secrets marked `sync: false`

Push the repo, create a Blueprint service, fill in `DATABASE_URL` and the GitHub
credentials, deploy.

### Fly.io (config included)

```bash
fly launch --no-deploy
fly secrets set DATABASE_URL="postgresql+psycopg://..." \
                SESSION_SECRET="$(python -c 'import secrets;print(secrets.token_urlsafe(48))')" \
                GITHUB_CLIENT_ID=... GITHUB_CLIENT_SECRET=...
fly deploy
```

`fly.toml` sets `release_command = "alembic upgrade head"`, so migrations finish
before new machines take traffic.

### Railway / any Docker host

Build `backend/Dockerfile`. Run `alembic upgrade head` as a release step, then:

```
uvicorn app.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips='*'
```

A `Procfile` with both lines is included.

### Why not Vercel

Vercel's serverless model is a poor fit for a persistent database pool and a
service that must run migrations as a release step. The brief explicitly says
not to force FastAPI into Vercel when it makes persistence or deployment
unreliable. Since the UI is server-rendered by the same service, there is no
static frontend to host separately anyway.

## 4. Migrations

Always a **release/pre-deploy step**, never at import time:

```bash
alembic upgrade head
```

Running them at import would mean every instance racing to migrate on every
boot. `alembic check` verifies the models and migrations agree.

## 5. Post-deploy checklist

```bash
curl https://your-domain/api/health         # {"status":"ok","environment":"production"}
curl https://your-domain/api/health/ready   # {"status":"ready","database":"connected"}
```

Then:

1. Visit `/signup`, create the first real account.
2. Promote it: `ember-admin grant-admin --email you@example.com` (or set
   `ADMIN_EMAILS` before signing up).
3. Create the first channel at `/channels`.
4. Post a message; confirm the poller picks up a second message in another
   browser within ~4 s.
5. Sign in from a different browser and confirm the unread count matches.
6. Confirm `/api/docs` returns 404 (docs are disabled in production).

## 6. Cookies and CORS

Single origin ⇒ the session cookie is `HttpOnly; SameSite=Lax; Secure`, scoped
to `/`, and **no CORS middleware is installed at all**.

If you ever split the UI and API across origins:

- set exact allowed origins — never `*` with credentials
- use `SameSite=None; Secure` and set `SESSION_COOKIE_DOMAIN`
- prefer sibling subdomains (`app.example.com` / `api.example.com`)
- if third-party cookie behaviour makes this unreliable, move to a short-lived
  access token with a rotating refresh token in an `HttpOnly` cookie — **never**
  `localStorage`

## 7. Operations

```bash
ember-admin list-users
ember-admin grant-admin --email someone@example.com
ember-admin stats
ember-admin purge-sessions      # expired sessions, OAuth states + email tokens
```

Run `purge-sessions` periodically (a weekly cron is plenty).

**Logs** — structured to stdout. Never contain passwords, tokens, cookies or
message bodies. Database errors are logged by exception type only.

**Backups** — use the provider's. Neon offers point-in-time restore; otherwise
`pg_dump "$DATABASE_URL" > ember-$(date +%F).sql`.

## 8. Deployment risks, identified up front

| Risk | Mitigation |
| --- | --- |
| Neon cold start after idle | `pool_pre_ping=True`, pooled connection string; expect one slow first request |
| Migrations racing across instances | Release-phase `alembic upgrade head` only |
| Rotating `SESSION_SECRET` | Invalidates stored GitHub tokens (if enabled) and any signed artefacts; existing sessions survive because tokens are random, not signed — but rotate deliberately |
| `redirect_uri_mismatch` on GitHub | The callback must match the OAuth app **exactly**; use separate local and production apps |
| Poll load as the cohort grows | Raise `POLLING_INTERVAL_MS`; see [POLLING.md](POLLING.md) |
| Connection-pool exhaustion on a small plan | `pool_size=10 + max_overflow=20`; lower it if the host caps connections |
| Free-tier instance sleeping | Use a paid tier or a keep-alive ping against `/api/health` |
| Forgetting `ENVIRONMENT=production` | Cookies would not be `Secure` and `/api/docs` would be public — the post-deploy checklist catches both |
| Reset/verification mail not arriving | Configure SPF/DKIM/DMARC on the `SMTP_FROM` domain; check the provider's suppression list |
| `REQUIRE_EMAIL_VERIFICATION` without SMTP | The app refuses to boot (nobody could confirm) — set SMTP first |
